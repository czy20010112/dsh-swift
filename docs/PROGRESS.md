### P2 的范围被调研改写了

原计划写的是"改 `exec.c` 的两个常量"。实测后这个估计不成立：

- flag 注入有**四处**，宿主侧（`ISHKernel.m`、`ISHShellExecutor.m`）两处在不同路径生效；
- 单独去掉 `--jitless` 会把 Sparkplug/Maglev/TurboFan 全打开，回到当初要规避的问题；
  上游的"默认模式"同时加了 `--no-sparkplug --no-maglev --no-opt`；
- 把堆放到 1GB 会让 OOM 从"V8 自己 abort"变成"整 App 被 jetsam 杀，会话一起丢"，
  因为当前 pin 的版本里内核匿名页上限形同虚设；
- 真正的提速手段是 **AOT 映像**（1.4x–3.9x），不是关 jitless（上游实测仅 10%）；
- 配置化路径（`ISH_NODE_MODE`）只在上游一个分支上，没进 master；本地 submodule
  落后 master **62 个提交**。

细节见 `PITFALLS.md` 第 18–22 条，决策理由见 `DESIGN-NOTES.md` 第 10 条。

## 新增的发现

### 过程分组不值得做（取消第 7 步）

两份设计文档都把"把一串连续工具折叠成一个过程区"当成必做项，还给了分组边界表
和组标题的组合规则。实测把这个前提推翻了。

连续工具段的长度分布（39,847 段）：

| 段长 | 占比 |
|---|---|
| **1 个** | **81.3%** |
| 2 个 | 17.5% |
| 3 个 | 0.8% |
| 4–5 个 | 0.3% |
| 6–10 个 | 0.04% |
| max | **8 个** |

p50 = 1、p90 = 2、p99 = 3。**根本没有"一串工具"**。

原因在打断事件的分布上：`assistant/message` 打断了 38,238 次分组，
占全部打断的 97.8%。agent 的实际节奏是"说一句 → 调一个工具 → 再说一句"，
而不是"闷头连调十个工具"。

**结论**：把 2 个调用折叠成「读取 2 个文件」只是多一次点击，信息量没减少。
分组取消，工具节点直接平铺。

这也省掉了设计文档里的 13 类工具名表和 22 字段优先级表中与分组相关的部分。

（顺带记一下最常见的两连组合，将来若做"相邻同类工具合并显示"可以参考：
`pwsh+pwsh` 2,375 / `read+read` 979 / `read+pwsh` 345 / `edit+edit` 306 / `grep+grep` 301。）


### `user-question-reply` 的 text 是 JSON 载荷，不是人话

形状是 `{kind, tool, questions:[...], answers:[{id, selected, custom}]}`。
原样渲染会让用户看到一坨带转义的 JSON。真实回答在 `answers` 里，
可能是选中的选项、也可能是自己打的字，或两者都有。

这条只出现 3 次（0.1%），所以很容易在小样本里漏掉——但它一旦出现就是满屏 JSON。

### `turn/end` 的 `reason` 有五种，非正常结束占 19.4%

`completed` 1,020 / `aborted` 138 / `error` 77 / `interrupted` 17 / `max-tokens` 13。
`aborted` 额外带 `reason` 字段、`error` 带 `error` 字段。

不显示结束原因的话，回答戛然而止时用户分不清是被打断、出错还是撞了 token 上限。
