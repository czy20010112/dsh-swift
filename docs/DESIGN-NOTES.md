# 设计决策

> 只记"为什么这样而不是那样"，并且只记**有过真实分歧**的决定。
> 没有争议的东西不写（代码自己会说）。坑记在 `PITFALLS.md`，进度在 `PROGRESS.md`。

---

## 1. 核心三层不依赖 UIKit

**决定**：`DshProtocol` / `DshSession` / `DshPresenter` 是纯 Swift，不 import UIKit 或 SwiftUI。
渲染层将来作为独立的 Xcode target 存在，依赖这三个模块，但不反向污染它们。

**为什么**：开发机装了 Swift 的 Windows 工具链，所以 `swift test` 在本地直接跑完
（88 个测试约 0.7 秒）。守住这条边界，改一行代码到看到测试结果是秒级；破掉它，
每次都要等 macOS runner 排队，迭代速度掉一个档。

CI 的 `test-linux` job 是这条边界的守卫——谁 import 了 UIKit，它立刻变红。

**代价**：装配器产出的是数据结构，不是视图。渲染层要自己做一次"节点 → 视图"的映射。
这个代价是值得的，因为那一层本来也要写。

## 2. 节点模型按实测分布设计，不照抄 web 端的 19 种

**分歧**：设计文档列了 19 种节点（照 web 端的 `ChatNode` 枚举），并把"思考块"
归在 Markdown 那一节里一笔带过。

**实测**（326 个会话 / 523,473 条事件）推翻了这个重点分配：

| 发现 | 数字 |
|---|---|
| `reasoning-chunks` 占全部事件 | **44.3%**（231,948 条） |
| reasoning 占正文体积 | **94.3%**（57.2 MB vs 正文 3.5 MB） |
| 前 5 个工具占全部调用 | **88.1%**（pwsh 一家 53.9%） |
| `user/message` 里真人写的 | **28.9%** |

**决定**：
- 思考块是**第一等公民**，而且是装配器要先做对的那一块；
- 工具专用卡只做 5 个（覆盖 88.1%），长尾 55 种走通用卡。web 端的 12 类专用卡
  是把预算花在 11.9% 上；
- 四档展示模式暂不做，只做 `standard` 一档作默认。

**代价**：和 web 端不是"节点种类一一对应"。接受——承诺是节点**语义**等价，不是像素一致。

## 3. 思考块默认收起，而且收起态只显示两个数字

**决定**：收起态是一行「思考 12.4 秒 · 3.4k 字」，展开才渲染全文。

**为什么是两个数字而不是首句摘要**：这两个值变化**不改变 cell 高度**，所以流式期间
可以每帧更新而不触发任何布局。如果收起态显示思考内容的首句，每来一个 token 都要
重新测量文本宽度。

44.3% 的事件走这条路径，所以它必须是最便宜的那条。

**为什么默认收起**：实测单轮思考动辄数千字。默认展开的话，用户每轮要先滚过
几千字才能看到结论。

## 4. 工具结果超过 8 KB 不进 cell

**决定**：`inlineResultLimit = 8192`，超过的走"查看全文"。

**依据**：结果长度 p50=421 / p90=5,292 / p99=27,437 / max=128,705 字符。
8 KB 这条线把 p90 放进内联、把 p99 挡在外面。

**为什么要有这条线**：不设限的话，p99 那些调用会让列表为了测**一个** cell 的高度
去排版两万多字。实测 `read` 的最大结果是 128,705 字符。

顺带发现：`pwsh` / `grep` / `web_fetch` / `job_output` 的最大结果都卡在 49,93x，
说明 host 侧对工具输出有 **50 KB 截断**。只有 `read` 能突破（它按行返回文件）。

## 5. 参数摘要优先显示 `description` 而不是 `command`

**决定**：摘要字段优先级的头两位是 `description`、`command`。

**依据**：实测字段频次 `description` 26,163 次、`command` 25,850 次——两者在 pwsh 上
几乎总是成对出现。而 `description` 是 agent 自己写的一句人话，`command` 是待执行的命令。

收起态只有一行，显示人话比显示 shell 命令有用。展开才看命令。

---

## 6. 配对走 `/connect`，默认声明 `interactions=answer`

**决定**：原生客户端走 `GET /connect?token=...&interactions=answer`，不走浏览器那条
`GET /?token=`。

**为什么**：详见 `PITFALLS.md` 第 1 条。简言之，走错端点会得到一个**只读客户端
且不报错**——能连上、流正常、但审批永远答不上。

**为什么默认 `answer` 而不跟随 host 的默认值**：host 默认 `none`。但手机 App 的存在
意义就是能在外面批准东西，默认只读等于默认没用。

---

## 7. 审批采用"谁先点谁生效"，不做设备独占

**背景**：一个 `approval/request` 会**同时**投递给所有 `interactions=answer` 的客户端
（电脑上的浏览器 + 手机 App 都算）。任一端答复就立即结算，其余端收到 `cancel` 帧。

**决定**：接受这个行为，不尝试让手机独占审批权。

**为什么**：host 侧没有提供独占的机制，要做只能靠客户端之间自己协调，
而那需要一个它们都信任的第三方——不存在。而且实际使用中两个设备点出不同答案的
情况极少。

**代价**：必须正确实现 `cancel` 帧的三种语义（见 `PITFALLS.md` 第 3 条），
并给三种终态不同文案。这部分有 18 个测试。

---

## 8. 待决交互用显式状态机，同一时刻只显示一条

**决定**：`InteractionSlot` 是一个显式状态机，`current` + `queue`，多出来的排队。

**为什么要状态机**：这条路径上有三个并发来源会任意交错——用户点按钮、host 发
`cancel`、连接断代。没有状态机就会出现"点了允许但卡片还在"或"卡片消失了但答复
没发出去"，而且都不报错。

**为什么只显示一条**：host 侧可以同时有多条 pending，但手机屏幕上并排两张审批卡
没法用。

**断代时把 pending 交还调用方而不是丢掉**：用户正等着那个审批，默默消失比
显示"已失效"更糟。

## 9. 线协议常量做成镜像 + 漂移闸门

**决定**：host 侧常量在 `WireConstants.swift` 里镜像一份，并用
`Tools/check-wire-drift.mjs` 在 CI 里与实际安装的 host 包对拍。

**为什么**：这些值改一个字符不会编译失败，只在运行时静默失效。它们是整个客户端
最脆弱的一层。

**它立刻证明了自己**：第一次运行就抓到设计文档写的 23 条转发事件实际是 28 条
（文档按 `0.1.7-rc.1` 的源码树数的，实际安装的是 `0.2.1-rc.5`）。

## 10. 远程档先行，设备内核在后

**决定**：先把"手机连一台跑着 `dsh web` 的机器"这条路走完，再碰 iSH 内嵌档。

**为什么**：远程档这条链上每一步只依赖一台远程机器，零环境风险。先做 iSH 的话，
一旦卡在内核级 bug 上，UI 一行都写不出来。

**iSH 调研把这个决定变得更正确**。原以为 P2 只是"改两个常量"，实测是：

| 原计划 | 实际情况 |
|---|---|
| 改 `exec.c` 一处 flag 注入 | **四处**，宿主侧还有两处在不同路径生效 |
| 去掉 `--jitless` 提速 3.6 倍 | 上游实测只有 **10%**；而且单删它会把 Sparkplug/Maglev/TurboFan 全打开，回到当初要规避的问题 |
| 512MB → 1GB | 代码里没有依赖，但当前 pin 的版本内核内存上限形同虚设（上游收紧的三个提交都不在），**OOM 会从 V8 自己 abort 变成整 App 被 jetsam 杀** |
| 真正的提速手段 | **AOT 映像**（1.4x–3.9x）。代价是 node 单模块 605MB `.S`、iOS objects 306MB、录一次 10 分钟、ABI 一变全部重录 |
| 配置化路径 | `ISH_NODE_MODE` 只在 `feat/aot-family-match` 分支，**没进 master**。本地 submodule 落后 master 62 个提交 |

**结论**：P2 不是"改两个常量"，而是"升级 submodule 62 个提交 + 对齐四处注入 +
把 AOT 录制纳入 CI"。这进一步支持把它放在远程档之后——远程档可用之后，
P2 失败也只是少一个内嵌档。

## 11. 不在 App 里做 NAT 打洞或中继

**决定**：App 只支持 (a) 局域网直连 + 手填/扫码 baseUrl，(b) 任意 baseUrl（含反代/
tailnet 地址）。跨网络的可达性交给 Tailscale 或使用者自己的网关。

**为什么**：把打洞做进 App 等于自己维护一个中继服务，那是另一个项目。
而且 Tailscale 已经把这件事做到了没必要重做的程度。

**鉴权的现实**：真 dsh 只有一个进程级 launch token（拿到即 owner、30 天、
无法单设备撤销、无轮换）。局域网自用够了；要上公网应该在 dsh 前面放一个
做真配对与撤销的网关，对 dsh 仍用 loopback + launch token。
